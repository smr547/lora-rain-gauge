# ADR-0001: Use a loss-tolerant, state-oriented LoRa application protocol

**Status:** Proposed  
**Date:** 2026-09-17

## Context

The LoRa rain gauge is the first spoke in a planned hub-and-spoke sensor system. Future spokes may report weather, tank level and other farm observations. Remote nodes are expected to be low-power appliances, while the base station receives messages and translates useful observations into SignalK.

The radio link must be assumed to be lossy. Experimental work has already demonstrated LoRa transport, CRC rejection, sequence numbering, timer wake, deep sleep and node-health telemetry. A rain gauge also has a particularly useful property: rainfall can be represented by a cumulative count of accepted bucket tips rather than by transmitting each bucket-tip event as an ephemeral message.

The system should remain simple. In particular, normal spoke operation should not require acknowledgement/retransmission handshakes, and monitoring/alarm policy should not be embedded in base-station firmware.

The protocol must also support multiple node and message types and remain maintainable over the lifetime of deployed appliances.

## Decision

We will use a small, versioned application protocol in which each LoRa frame contains:

1. a common protocol envelope; and
2. exactly one message-type-specific payload.

The protocol will favour **absolute, idempotent sensor state** over transient events where the sensor permits it.

For the rain gauge, the spoke will transmit a cumulative accepted bucket-tip count. The base station will retain the raw received state and derive incremental rainfall from changes in the cumulative count.

The common envelope will provide sufficient information for framing, protocol evolution, node identity, boot/session identity, sequencing and payload interpretation. Sensor-specific measurements will not be placed in a monolithic common structure.

Protocol version, message type and payload version are distinct concepts:

- **protocol version** identifies the rules of the common wire protocol;
- **message type** identifies the meaning of the specialised payload;
- **payload version** permits a particular message type to evolve without forcing unrelated deployed sensor types to change protocol version.

Receivers will treat unknown but otherwise valid message types or payload versions as unsupported data, not as corrupt radio frames.

Normal operation will not use an acknowledgement/retransmission handshake. Lost packets are tolerated; a later absolute-state message allows the receiver to recover current state. Sequence numbers remain useful for duplicate, out-of-order and communications-loss diagnostics.

The base station will publish both:

- raw/protocol observations useful for engineering and diagnostics; and
- derived sensor observations, such as newly observed bucket tips/rainfall.

User-facing accumulation periods and alarm policy (for example rain since midnight, rain since 09:00, or a node-not-seen alarm) remain downstream concerns and are not embedded in the LoRa protocol or base-station firmware.

A node will be able to report its appliance/firmware provenance through a specialised identity message. This will include enough information to associate a deployed appliance with the source repository and immutable source revision from which its firmware was built. Firmware provenance should be generated by the build process rather than maintained manually.

## Reliability semantics

The design deliberately does **not** guarantee delivery of every packet. Instead, it aims to ensure that later packets contain enough state to recover from ordinary packet loss.

The receiver must explicitly handle:

- corrupt frames;
- lost packets;
- duplicate packets;
- out-of-order packets;
- deep-sleep wake;
- hard reset / new boot session;
- complete node power loss;
- base-station outage and restart;
- sequence and counter wrap; and
- physical node replacement.

A boot/session identifier distinguishes a new node execution session from ordinary deep-sleep wake. The node identifier identifies the appliance independently of its boot/session.

The base station requires durable receiver state sufficient to avoid losing protocol continuity across a base-station restart. The exact base-station platform and persistence mechanism remain open design decisions.

There is a recognised loss window: if the base station has not received some accumulated tip count and the node subsequently loses the volatile/RTC state containing those tips before reporting them, those observations cannot be reconstructed unless additional non-volatile node persistence is introduced. Version 1 will quantify and explicitly accept or mitigate this risk rather than hiding it.

## Consequences

### Positive

- Occasional packet loss does not normally lose rainfall totals.
- Remote nodes avoid receive windows and retransmission handshakes, supporting low-power operation.
- The protocol remains independent of SignalK.
- New sensor types can be added without growing every packet into a union of all possible sensor fields.
- Raw observations remain available for diagnostics while downstream consumers receive useful derived observations.
- Firmware provenance makes deployed appliances traceable back to their source and documentation.

### Costs and trade-offs

- The base station must retain per-node protocol state.
- Reset/session semantics must be carefully specified.
- Some rare combinations of base-station outage and node state loss can lose observations.
- Protocol evolution rules and message registries must be maintained.
- A small amount of additional identity/version metadata is carried in each frame.

## Alternatives considered

### Transmit individual bucket-tip events

Rejected for the primary rainfall representation because a lost packet would directly lose rainfall unless acknowledgements/retransmission were added.

### Reliable acknowledged LoRa messaging

Not selected for Version 1. It increases radio-on time, state-machine complexity and coupling while providing little benefit when absolute sensor state can self-heal after ordinary loss.

### Transmit SignalK deltas directly from sensor nodes

Rejected because it couples low-power spokes to SignalK semantics and makes the radio protocol less suitable for other consumers and future sensor types.

### One fixed telemetry structure containing every possible field

Rejected because future sensor types would force unrelated nodes to carry irrelevant fields and would make protocol evolution unnecessarily coupled.

## Follow-up decisions

Separate decisions/specification work are still required for:

- exact field widths and byte order;
- CRC choice and coverage;
- radio PHY/deployment settings;
- node identity allocation;
- boot/session identifier generation and persistence;
- base-station durable-state implementation;
- rain-gauge counter persistence policy;
- exact SignalK path mapping; and
- base-station hardware platform.
